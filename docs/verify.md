# 下载状态机与校验策略

`ggufget` 的下载不是"拿一个 HTTP 响应写到文件里"那么简单。文件可能有几个 GB，网络随时会断，服务器可能限流，用户可能按 Ctrl-C。这篇文档说明它在磁盘上留下了什么、什么时候才算成功、以及为什么校验策略是分级的。

## 磁盘上的文件

| 文件 | 作用 |
| --- | --- |
| `<name>.gguf` | 最终文件。**只有校验通过后才会出现** |
| `<name>.gguf.part` | 正在写入的数据 |
| `<name>.gguf.part.seg` | 分段进度 journal（仅分段模式） |

单段模式只用到 `.part`；分段模式额外维护 journal。

## 状态机

```
                         ┌──────────────┐
   probe (Range: 0-0) ──▶ │ total, etag  │
                         └──────┬───────┘
                                │
        ┌───────────────────────┴───────────────────────┐
        │ 已存在同名最终文件？                            │
        │   是 → 校验：通过则跳过（Skipped=true）          │
        │        失败 → 需 --overwrite 才覆盖             │
        └───────────────────────┬───────────────────────┘
                                │
                    ┌───────────┴───────────┐
        total ≥ 64 MiB 且支持 Range     否则 / 不支持
                    │                       │
          ┌─────────┴─────────┐     ┌───────┴────────┐
          │ 分段：4 连接并发    │     │ 单连接顺序写    │
          │ + journal 续传     │     │ 按大小续传      │
          └─────────┬─────────┘     └───────┬────────┘
                    └───────────┬───────────┘
                                │
                       校验（见下节）
                                │
                    ┌───────────┴───────────┐
                    │ 通过 → rename 成正式名  │
                    │ 失败 → 删除 .part      │
                    └───────────┬───────────┘
                                │
                          删 journal 收尾
```

### 前置检查

下载前会检查磁盘剩余空间：`需要 = total - 已有 + 64 MiB`。不足直接以退出码 5 结束，而不是下到一半才失败。

### 已存在的文件

默认不覆盖。先校验：通过则报告“已存在，跳过”，失败则报错；想覆盖就加 `--overwrite`。这样重复运行同一条命令是安全的。

## 续传的依据

### 单段模式

按 `.part` 的**当前大小**发 `Range: bytes=N-`。

### 分段模式

按 journal 里每段的 `done`：

```json
{"version":1,"total":369358144,"etag":"3ABDFC690FB9C07E6D1F5D1E2C9A9F1A-145",
 "segments":[{"start":0,"length":92339536,"done":44710580},
             {"start":92339536,"length":92339536,"done":47446700},
             {"start":184679072,"length":92339536,"done":46660267},
             {"start":277018608,"length":92339536,"done":48315051}]}
```

- journal 每 2 秒用**原子写**（写临时文件再 rename）落盘，避免断电留下半个 JSON。
- 恢复时校验 `total` 和 `etag`（`version` 字段目前只记录）：任一不匹配就**重新切分**，因为服务器上的文件已经变了。把两个版本的数据拼在一起是我能想到最糟糕的失败模式。
- 每段独立发 `Range: bytes=start+done-end`，所以 4 个连接可以各自续传。
- 全部结束后再核对一次"每段 done == length"，并且 `fsync`，然后才进入校验。

## 校验策略

`--verify` 有四个值：

| 值 | 行为 |
| --- | --- |
| `auto`（默认） | 见下方决策表 |
| `size` | 只核对总字节数 |
| `sha256` | 总是核对 SHA256 |
| `off` | 什么都不查（只在你确定来源可信时用） |

`auto` 的决策：

| 条件 | 是否算 SHA256 |
| --- | --- |
| 镜像给出了 SHA256，文件 ≤ 4 GiB | 算 |
| 镜像给出了 SHA256，文件 > 4 GiB，**首次下载** | 不算（省几分钟） |
| 镜像给出了 SHA256，文件 > 4 GiB，**续传或重试过** | 算 |
| 镜像没给 SHA256 | 不算 |

理由：大文件首次下载已经有 ETag + 总大小 + 分段完整性三层保护，而全量哈希要额外读一遍 7 GB。但**一旦这次下载经历过中断或重试**，风险变了，就值得花那几分钟。

哈希来源：Hugging Face 的 `siblings[].lfs.sha256`，或 ModelScope 的 `Files[].Sha256`。

### 失败时

- 哈希不符 → **删除 `.part`**，返回退出码 4，并打印期望值与实际值；下载后大小不符 → 报错（退出码 1），保留 `.part` 供续传。
- 删除而不是保留，是为了不让下次运行在坏数据上"续传"。

## 并发数与限流

- 分段模式的连接数：`--connections`，默认 4。文件小于 64 MiB、镜像不支持 Range，或连接数 < 2 时退回单连接。
- 镜像返回 `429 Too Many Requests` 或 `503`：
  - 按 `Retry-After`（缺省用指数退避，500 ms 起，上限 30 s）等待；
  - **并发数减半**；
  - 计入重试次数（`--retries`，默认 3）。
- 无数据超时（默认 15 s）：取消该段请求并重连；整个下载被取消时保留 `.part` 供续传。

## 为什么不用 `Content-Length` 判断完成

`Content-Length` 只是服务器"声称"的长度，中断的 TCP 流和完整的流看起来可以一样。`ggufget` 以 Range 探测出的**总大小**为准（`Content-Range: bytes 0-0/<total>`），下载完再核对一次 `stat` 的大小，最后才看哈希。

## 与 LM Studio 的衔接

下载完成后：

1. 文件位于 `<模型目录>/<文件名去扩展名>/lmstudio-ai/<文件名>.gguf`（默认 `--layout lmstudio`；`repo` 布局为 `<模型目录>/<发布者>/<仓库>/<文件名>.gguf`）；
2. 如果有 `lms` CLI，会执行 `lms ls --json` 并检查这个相对路径是否出现在列表里；
3. 出现 → 提示"已可被索引"；没出现 → 提示重启 LM Studio 或检查模型目录；
4. 没有 `lms` → 跳过检查，只给一句目录提示。

另外，如果下载过程中有 `.part` 残留但最终文件已存在（上一次成功后被中断的重复运行），会按"已存在"处理，不会重复下载。
