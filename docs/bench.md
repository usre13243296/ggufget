# 镜像测速：方法与原始数据

本文记录 `ggufget` 立项时的测速方法、原始数字和注意事项。所有数字都是**单机单次**测量，网络是会变的，请以你自己机器上的 `ggufget doctor` 为准。

> 测量时间：2026-11-22 前后；单机单次，具体带宽、运营商与是否走代理未记录。数字只用于判断量级，不要当基准。文中保留原始记录的 KB/s、MB/s（十进制）与 MiB/s（1024 进制）；换算：1 MiB/s = 1.048576 MB/s。

## 方法

### 1. Range 分片计时（手工）

对同一个文件发一个 `Range: bytes=0-<n>` 请求，只统计"连接建立到收满 n 字节"的时间：

```
速度 = 收到的字节数 / 耗时（秒）/ (1024 * 1024)   # MiB/s
```

- 分片 256 KiB 用于测 LM Studio 官方代理（它的行为接近小分片拉取）；
- 分片 5 MiB 用于测 hf-mirror 和 ModelScope；
- 另外用 20 MB 的完整下载检查是否会断流。

### 2. `ggufget doctor`（可复现）

`doctor` 走同一条逻辑：对每个镜像列表 → 取最小的 gguf → 请求前 4 MiB → 按已读字节计时，20 秒超时。（v1.2.1 的 `doctor` 文案写作 8 MiB，实际取样是 4 MiB，以代码为准。）

它**串行**测速：三个并发测速会抢同一条带宽，排名就没有意义。慢镜像会被超时截断，但已读到的字节数仍然描述它的真实速度。

```sh
ggufget doctor
```

## 原始数据

### LM Studio 官方代理（`search.lmstudio.ai/v1/hf-proxy`）

| 测试 | 结果 |
| --- | --- |
| 256 KiB 分片 | 48.5 s → **≈ 5 KB/s** |
| 20 MB Range | 读到 15,709,430 / 20,971,520 字节后 `IncompleteRead` |

对小分片极慢、对大请求直接断流，这是典型的"代理转发+限速"表现。

### hf-mirror.com

| 测试 | 结果 |
| --- | --- |
| 20 MB 完整下载 | 136 KB/s |
| 5 MB 分片 | 692 KB/s |
| `doctor` 抽样（晚高峰） | 3.4 MiB/s |
| `doctor` 抽样（另一时段） | 0.13 MiB/s |

波动很大，但**可用**。

### ModelScope（modelscope.cn）

| 测试 | 结果 |
| --- | --- |
| 5 MB 分片 | 8,486 KB/s ≈ **8.5 MB/s** |
| `doctor` 抽样（拥塞时段） | 0.1 MiB/s |

最快，但**覆盖不全**：测试用的 `FPHam/Clever_Sydney-4_12b_GGUF` 在 ModelScope 上两次 API 探测都是 404。

### 汇总

| 来源 | 最好 | 最差 | 结论 |
| --- | --- | --- | --- |
| LM Studio 官方 | 5 KB/s | 断流 | 不可用 |
| hf-mirror | 3.4 MiB/s | 0.13 MiB/s | 覆盖最全 |
| ModelScope | 8.1 MiB/s（8.5 MB/s） | 0.1 MiB/s | 最快但缺模型 |

**7.3 GB 文件的时间估算**：官方代理 ≈ 2.7 小时（且大概率中断）；hf-mirror 0.7 MB/s 时 ≈ 2.7 小时；ModelScope 8.5 MB/s 时 ≈ 15 分钟。

同一台机器上两个源能差 12 倍，这正是 `ggufget` 要"探测后再选"而不是"写死一个镜像"的原因。

## 端到端验证

用 `ggufget` 真实下载 `lmstudio-community/Qwen2.5-0.5B-Instruct-GGUF` 的 `Q3_K_L`：

- 大小 369,358,144 字节（352.2 MiB）；
- 切成 4 段，每段约 92.3 MB，`.part.seg` journal 每 2 秒落盘；
- 用时 **662 秒**（当时镜像约 0.57 MB/s）；
- `--verify sha256` 通过，`.part` 改名为 `.gguf`；
- 过程中 4 个连接都在推进，journal 的 `done` 单调递增。

## 注意事项

1. **单次测量不代表长期速度**。同一个镜像在两个小时内可以从 0.1 MiB/s 变到 3.4 MiB/s。
2. **代理会改变一切**。开了代理时，决定速度的是代理的出口，而不是镜像本身。
3. **DNS 污染会影响"能否连上"**。`huggingface.co` 在某些网络里被解析到无关网段，`doctor` 会显示超时而不是慢。
4. **`hf-mirror` 只镜像文件，不镜像 API**。`/api/models` 会 308 跳回 `huggingface.co`，所以 `search` 的可达性取决于 hf.co，`list`/`get` 不受影响（它们用的是同一个 API，跳转会被跟随）。
5. **小分片测速会低估快镜像**。TLS 握手和首字节延迟在 5 MiB 分片里占比不高，但 256 KiB 分片里占了大头——这正是官方代理看起来只有 5 KB/s 的原因之一，即使扣除握手开销它也慢得离谱。
